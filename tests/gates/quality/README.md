# Static analysis and architecture gate

This dependency-free Python 3 gate checks production C/H files in `01_application`, `02_device`,
`03_platform`, `04_impl`, and `06_utils`. It never accesses `.claude` and never modifies
`05_vender`. Vendor discovery is deliberately limited to the reviewed `05_vender/freertos` and
`05_vender/segger_rtt` package roots.

## Run

From the repository root:

```sh
./tests/run_quality.sh
python3 -B -m unittest -v tests/gates/quality/test_quality_gate.py
```

The gate prints text and JSON, writes `build/quality/quality-report.json` by default, and returns
nonzero for any mandatory failure. Override the report path with `QUALITY_JSON_OUT`. `clang-format`,
`clang-tidy-18`, and `cppcheck` are mandatory; a missing tool is a structured hard failure rather
than a `SKIP`. Requiring the versioned executable prevents an unrelated preinstalled Clang release
from silently changing the analyzer contract.

Every report carries a UUID and an input fingerprint covering production and test-header inputs, all
three reviewed baselines, the two closed-set vendor packages, formatter/analyzer identities and
versions, the fixed analyzer rule configuration, and the CMake files that define host compile
commands. It also records an `analysis_input` object containing the normalized filtered compile-DB
digest, every selected translation unit's `file`, `directory`, and `command`/`arguments` contribution,
the resolved C compiler identity/version, and—when the DB is generated automatically—the CMake
identity/version. Ephemeral build roots and output paths below them are normalized, so rebuilding the
same inputs in a different temporary directory does not invalidate a report. A compiler, flag, source
command, analyzer, or configuration change does invalidate it.

A PASS is valid only for that fingerprint. Verify a standalone report with:

```sh
python3 tests/gates/quality/quality_gate.py \
  --verify-report build/quality/quality-report.json
```

Verification regenerates the temporary host compile DB with the same fixed CMake arguments. If the
report was generated by a full CMake build or any invocation using an explicit DB, verification must
receive that same DB:

```sh
python3 tests/gates/quality/quality_gate.py \
  --compile-db /path/to/build/compile_commands.json \
  --verify-report build/quality/quality-report.json
```

## Architecture rules

- `01_application` may directly include `01_application`, `02_device`, `03_platform`, and
  `06_utils`. This is intentional: applications consume vendor-neutral platform services directly.
- `01_application/board/**` is the composition root and additionally may combine implementation and
  vendor objects.
- `02_device` may include `02_device`, `03_platform`, and `06_utils`; vendor headers and vendor types
  are rejected.
- `03_platform` may include its own layer, `06_utils`, and only the ops/opaque-context declarations
  in `04_impl/common`; concrete backends and vendor types/headers are rejected.
- `04_impl` may include only `04_impl`, `05_vender`, and `06_utils`; upward includes fail.
- `06_utils` may include only itself and standard headers. The four existing upward/vendor includes
  are individually reviewed architecture debt, not a layer-wide exception.
- Production files may not include test mock/contract headers.

`architecture_baseline.json` identifies each reviewed finding by exact path, rule, token, normalized
line SHA-256, and same-line occurrence number, with a mandatory rationale. New findings, changed
metadata, duplicate IDs, malformed entries, and stale entries all fail. Never add wildcards, directory
exceptions, or rule-wide exceptions.

## Vendor integrity

`vendor_checksums.sha256` is a repository-owned reviewed baseline because upstream files under
`05_vender` are immutable and cannot carry a local manifest. It uses standard `sha256sum` records
whose filenames are repository-relative. The gate:

1. requires the baseline to exist;
2. accepts paths only within `05_vender/freertos` and `05_vender/segger_rtt`;
3. rejects malformed, escaping, duplicate, missing, and hash-mismatched entries; and
4. closed-set scans exactly those two package roots and rejects every unlisted file.

There are currently no ignore patterns: every regular file in both package roots is reviewed. The
STM32CubeMX subtree is intentionally outside this baseline.

To refresh after an explicitly reviewed upstream package replacement:

```sh
find 05_vender/freertos 05_vender/segger_rtt -type f -print0 \
  | sort -z | xargs -0 sha256sum > tests/gates/quality/vendor_checksums.sha256
```

Review the complete diff before accepting it. Never edit vendor files to make hashes match.

## External static analyzers

The hard gate runs both analyzers over all production `.c` translation units in
`01_application`, `02_device`, `03_platform`, `04_impl`, and `06_utils`. It filters the host test
compile database down to those files before invocation, so `05_vender`, test sources, contracts,
and generated mocks are never analyzer inputs. The filtered database must cover the complete
production set (currently 69 translation units), otherwise the gate fails.

- `clang-tidy` enables the Clang core analyzer, malloc ownership/size checks, suspicious `sizeof`
  expressions, and suspicious memory comparisons.
- `cppcheck` enables its `warning`, `performance`, and `portability` groups in C11 mode.

These sets deliberately favor actionable correctness diagnostics over broad style churn. Every
analyzer diagnostic is converted to a report violation containing rule, production path, line,
token/check ID, and message. There are no global diagnostic suppressions. If a future tool false
positive is unavoidable, use only a source-local, check-specific suppression with a reason.

A full `tests` CMake build exports `compile_commands.json`, and the quality target/CTest entry reuse
it via `--compile-db`. Standalone `./tests/run_quality.sh` and the standalone quality CMake project
configure the host tests only long enough to create a database in an automatically removed `/tmp`
directory; no analysis build directory is created in the source tree.

## Formatting and float rules

`clang-format --dry-run --Werror --style=file` covers every production C/H file using the repository
`.clang-format`. Decimal/hex floating constants require an `f`/`F` suffix, and standard math calls
must use their `f` variants; comments and literals are masked before scanning.

`float_baseline.json` uses the same precise finding identity model for irreducible legacy findings.
A new finding fails and a finding that disappears makes its entry stale. The current baseline is
empty because directly fixable float findings must be fixed rather than grandfathered.

## Self-tests and CMake

The negative fixtures cover every forbidden layer direction, the legal `01_application ->
03_platform` path, the board exception, exact architecture baseline new/stale behavior, vendor
neutrality, test-header leakage, mandatory formatting, float rules and stale float entries, required
vendor baseline behavior, checksum tampering, escaping/duplicate/missing paths, unlisted vendor
files, nonzero exits, missing mandatory analyzers, structured failures from real clang-tidy and
cppcheck diagnostics, complete compile-command coverage, and stale PASS rejection.

The child CMake project is standalone and does not require editing `tests/CMakeLists.txt`:

```sh
cmake -S tests/gates/quality -B build/quality-cmake
cmake --build build/quality-cmake --target quality
ctest --test-dir build/quality-cmake --output-on-failure
```

It exposes the `quality` target and `quality_gate` / `quality_selftest` CTest entries.
