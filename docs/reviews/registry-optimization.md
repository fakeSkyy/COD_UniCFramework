`util_registry` 的一次性能优化记录（2026-07-31）。它是 impl 层各后端把 HAL 中断回调路由回所属 context 的查找表，`UTIL_Registry_Find` 位于每次中断的热路径上。

## 结果

以 CAN 接收路由为例（容量 16、实际注册 4 个节点），`Find` 的开销：

| 阶段 | 未命中 | 命中第 3 项 | 循环体指令/轮 |
| --- | --- | --- | --- |
| 优化前 | ~240 周期（1.4 µs） | ~45 周期 | 10 |
| 加 count 上界 | ~40 周期（0.24 µs） | ~30 周期 | 7 |
| 改指针游走 | ~28 周期（0.17 µs） | ~21 周期 | 5 |

累计约 8.5 倍。周期数按 Cortex-M4 @168 MHz 估算，指令数取自 `arm-none-eabi-objdump` 实测；**无硬件在环实测**。

## 改动一：注册表改为 append-only，查找上界由 capacity 改为 count

优化前 `Find` 的循环上界是 `capacity` 而非实际条目数，因此未命中恒定走满全表——容量 16、只注册 4 个节点时，未命中仍比较 16 次。这是当时最大的单项浪费。

要让 `count` 成立，条目必须无空洞，也就是不能有 `Remove`。而 `Remove` 的存在源于一个概念混淆：注册表被同时用来回答两个问题。

- **所有权**：这个外设句柄属于哪个 context —— 实例级，创建后恒定。
- **布防状态**：现在要不要投递 —— 随启停变化。

ADC 和 UART 后端让注册表兼任了后者（未布防时表里没有条目，`Find` 返回 NULL，回调自然不投递），于是 Add/Remove 被绑在了 start/stop 上。解耦方式是让注册表只管所有权，布防状态回到 owner 自己的字段：

| 后端 | Add 位置 | 停止时的动作 | 回调的投递判据 |
| --- | --- | --- | --- |
| ADC | `CreateCtx` | `mode = ADC_MODE_IDLE` | `a->mode` |
| UART | `CreateCtx` | 清 `rx_buf` | `u->rx_buf != NULL` |
| CAN | `start`（每节点一次） | — | — |

两个判据字段本来就存在，不需要新增。CAN 的 `start` 失败回滚里那两处 `Remove` 也去掉了：未启动的总线上残留条目不可达，而 `filter_add` 的副作用本来无法回滚，两者都保留才一致。

`UTIL_Registry_Remove` 随后从 API 删除。这样"只增不删"由**函数不存在**保证，而非依赖调用约定 —— `util_registry` 位于 `06_utils`、自述为硬件无关的通用组件，后续接入新外设的人不会知道有这条隐含前提。

发布顺序相应调整为 **value → key → count**：并发 `Find` 受 `count` 约束，在 count 写入前无法到达该槽，届时两个字段都已就位。

### 顺带修掉的一个 bug

`uart_route` 同时服务接收、发送完成、错误三个回调，但原先 Add/Remove 只挂在**接收**启停上。后果是只发不收的用法（日志输出、单向下发指令）下，`PLAT_UART_OnSendComplete` 与 `PLAT_UART_OnError` 注册的回调永不触发 —— `Find` 返回 NULL 后静默丢弃。注册移到 `CreateCtx` 后两者恢复工作。

### 引入的一个新情况

路由条目现在跨越 `stop_rx` 存活，因此 `stop_rx` 时已挂起的 RX 事件仍会进入回调。原先靠 `Remove` 使其不可达，现在 `HAL_UARTEx_RxEventCallback` 显式判 `rx_buf == NULL` 并直接返回 —— 否则会用调用方已收回的缓冲区投递、甚至重新布防。

## 改动二：Find / ForEach 改为指针游走

把索引循环 `for (i = 0; i < n; i++) slots[i]` 改为游标循环 `for (s = slots; s != end; s++)`。省掉每轮的 `lsl #3` 地址计算和 `uxth` 索引截断。

额外收获：改前为同时保住基址与命中槽地址多占一个寄存器，触发了栈帧；改后游标本身即槽地址，寄存器压力下降，函数变为叶子函数，`push {lr}` / `pop {pc}` 一并消失。整体 FLASH 减少 32 字节。

语义、内存布局、并发保证、`ForEach` 的注册顺序均未改变 —— 这是代码生成层面的优化，不是换数据结构。

`UTIL_Registry_Add` 保留索引写法：它只在任务上下文、每实例一次，不在热路径上，且其索引形式与 `n`/`capacity` 边界比较、`slots[n]` 发布顺序连在一起读更清楚。

## 评估过但未采用的方案

同条件编译（`-Og`，字段同为 volatile）实测的循环体开销：

| 方案 | 指令/轮 | 周期/轮 | 4 节点未命中 |
| --- | --- | --- | --- |
| 当前（指针游走数组） | 5 | ~7 | ~28 |
| 侵入式单链表 | 4 | ~6 | ~24 |
| 开放地址哈希（32 槽） | 5 + 3 固定 | ~7 | ~10 |

**链表**：每轮仅快约 4 周期，代价是放弃"条目位于连续内存、遍历必定在 count 轮内结束"的结构性保证。两次 load 构成依赖串（须先取 `next` 才能读 `key`，M4 上无法重叠），优势主要来自省掉边界比较而非访问模式更优。收益最小、结构性损失最大，不采用。

> 注：只增不删消除了链表摘除节点后重新加入导致遍历回到表头的 ABA 风险 —— 该风险仅存在于有 `Remove` 的模型。

**哈希表**：唯一能显著改善的方案（约 4 倍，未命中 ~10 周期）。只增不删也消除了墓碑累积问题。但仍有两项实际代价：

1. 性能开始依赖调用方选择的 key。CAN 路由的 key 是 `id + 1`，电机常用的 0x201–0x208 连续 ID 分布良好；但步长 32 的 ID（0x200 / 0x220 / 0x240）在 32 槽表中全部冲突，退化为满链，最坏仍是 O(capacity)。框架无法约束调用方的 ID 选择。
2. `06_utils` 这一硬件无关的通用层需承担散列策略：指针 key 因对齐低位为 0 必须折叠，整数 key 不需要。硬编码一种折中，或参数化哈希函数 —— 后者在 ISR 中引入一次函数指针调用，抵消掉节省的周期。

此外 `ForEach` 因表有空洞而变慢（CAN 的错误广播走它）。

**结论**：不采用。绝对收益仅约 0.18 µs，而 1 Mbit/s 下最短 CAN 帧为 47 µs（占 0.4%），且 `HAL_CAN_GetRxMessage` 本身即需上百周期。若单条 CAN 总线未来需挂数十个节点，届时再引入哈希，并需在文档中明确 ID 选择会影响性能。

## 附带效应：容量超配不再有运行时代价

查找上界改为 `count` 后，`capacity` 只影响静态内存（每槽 8 字节），不再影响查找耗时。因此容量常量（`CAN_NODES_PER_BUS`、`UART_ROUTE_MAX` 等）可按最坏情况放宽，无需为省时间而收紧。

## 使用约束

- **`Add` 只在任务上下文调用**，`Find` / `ForEach` 无锁且 ISR 安全。多核目标需外部保护 `Add`。
- **注册应在 `CreateCtx` 完成**，代表所有权；随运行变化的状态放在 owner 自己的字段里，由回调在查找后判断。
- **key 不得为 NULL**（NULL 作空槽哨兵）。整数 key 需偏置，CAN 路由用 `id + 1`（见 `id_key()`），否则 ID 0 不可寻址。
- **不要为 `util_registry` 重新引入 remove**。若确有需要移除条目的场景，应先重新评估上文的全部权衡 —— 本次优化的正确性基础就是 append-only。

## 复核记录(2026-09-02)

上面那句「**没有 `Remove`**」当天成立,现在**不再成立**:`UTIL_Registry_Remove` 已加回。

正文不改 —— 按 `docs/ai-memory/docs-drift-audit-method.md` 的规矩,那是当次测量的记录。但这一条
需要说明,因为它推翻的是本文的核心设计结论,不只是一个数字。

**为什么加回来。** CAN 后端的 `IMPL_STM32_CAN_DestroyCtx` 只做 `IMPL_free(ctx)`,而 `CreateCtx`
把这个 ctx 按接收 id 注册进了 `bus->route`。free 之后路由表留着野指针,而接收路径在**中断上下文**
里解引用它(`c->rx_cb`,然后 `c->arg`)。没有 `Remove` 就没法修 —— 这是 append-only 这个决定的
真实代价,当时没有被发现,因为生产代码里没有任何调用者销毁 CAN 节点。

**本文的核心论证仍然成立。** 「要让 `count` 成立,条目必须无空洞」—— 对的,所以新的 `Remove`
**不压缩表**:它就地清 key,`count` 变成高水位而不是活跃条目数,`Add` 优先复用被退休的槽位。
压缩(把末尾条目搬进空洞)看起来更整洁但不安全:先减 `count` 会让被搬动的条目短暂不可达,于是
一个查**无关 key** 的 ISR 会在那个窗口里漏掉它。

所以准确的说法不是「append-only 错了」,而是:**无空洞是 `count` 上界的前提,而墓碑法在不引入
空洞语义的前提下提供了删除** —— `Find` 的循环一个字没改,仍然是 `count` 上界 + 指针游走。
