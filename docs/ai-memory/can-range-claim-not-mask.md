# 一个节点认领一段 id:用范围,不用掩码

## 需求

四个 M3508 各自在 `0x200 + ESC id` 上报,拨成 1..4 就是 `0x201..0x204` 连续四个 id。
原来每个轮子一个 CAN 节点(5 个节点),想收成一个。

## 为什么不用掩码

掩码只能表达"某些位任意",所以它覆盖的必然是一个**2 的幂长度、且对齐**的区间。
`0x201..0x204` 长度 4 但**不对齐**(起点不是 4 的倍数),所以没有掩码正好覆盖它。

最窄的能覆盖它的掩码是 `id & 0x7F8 == 0x200`,也就是 `0x200..0x207`。多收进来的是:

| 多收的 id | 是什么 |
|---|---|
| `0x200` | **DJI 的电机控制帧** —— 我们自己发的 |
| `0x205`/`0x206`/`0x207` | GM6020 的反馈(id 1/2/3) |

多收不是"浪费一点 CPU":`0x200` 是本机发出的控制帧,把它收回来会让 `on_feedback` 拿一帧
不是反馈的数据去解算。**所以掩码在这里不是次优方案,是错的。**

## 两个后端只好不一样,这是对的

- **H7 / FDCAN** 有 `FDCAN_FILTER_RANGE`,一个滤波元件精确表达 `[first, last]`。
- **F4 / bxCAN** 没有精确范围滤波器。所以 F4 后端**把整段展开**成逐 id 的滤波槽 + 逐 id 的
  注册表条目。

调用方两边都拿到:一个节点、一个回调、一次 teardown。**差异被吸收在后端里,而不是泄漏成两套
API** —— 这正是 ops+context 那层存在的目的,这是它第一次被真正考验。

代价写清楚:F4 上一段 N 个 id 吃 N 个滤波槽,H7 吃 1 个元件。所以"能不能认领一段"这个能力在
两个芯片上的**容量含义不同**,不要按 H7 的余量去规划 F4。

## 一个把我引偏的数字

我先跟用户说 FDCAN1 有 8 个滤波"id",于是省槽位的动机看起来很强。实际是 **8 个元件**,
dual 模式下每元件 2 个 id = 16 个 id(再被 `CAN_NODES_PER_BUS` 限住)。**动机比我以为的弱**,
但结论没变 —— 因为真正的理由从头到尾是"掩码会多收",不是"省槽位"。

顺带一个实现上的坑:滤波器分配表必须**按元件索引**,不能按 id 索引。RANGE 元件独占一整个元件,
DUAL 元件装两个 id —— 两种模式每元件装的 id 数不同。我第一版混用了 `slot/2` 和 `slot`,
必须整个重写。`filter_max` 也要是元件单位(`hfdcan->Init.StdFiltersNbr`);我改了 `filter_count`
的单位却漏了 `filter_max`,是一条**既有的**测试
(`test_bus_and_filter_capacity_follow_hardware_limits`)抓住的。

## 测试上的一课

"断言调用了几次 filter 配置函数"**抓不到 RANGE 退化成掩码** —— 次数一样。必须捕获传进去的
结构体并断言 `FilterType == FDCAN_FILTER_RANGE` 以及两个端点。

**断言的是行为不是调用次数。** 参见 [[host-tests-blind-spots]]。

## 未解决的:连号是硬件契约

`CHASSIS_FIRST_ESC_ID` 起连续四个,是**拨码开关上的约定**,编译期没有任何东西能发现它被破坏。
拨成 1/2/5/6 就只能选:更宽的范围(放进本模块不拥有的 id),或者一个轮子一个节点。
`chassis_init` 只能在运行时检查这段是否连续并拒绝启动 —— 这是**能做到的最强保证**,不是理想的。
